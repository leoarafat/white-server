ARPMUSIC
Partner API · v1

Deliver to ARP Music from your own system

Push releases, follow every status change, and request VEVO channels — without anybody logging into a dashboard. Written for the engineer doing the integration; you should be sending your first release inside an hour.

This version delivers music videos. Every release carries a video file and can carry a VEVO channel. If you need audio-only releases too, tell your account contact.

Getting started

Every request goes to https://api.arpmusic.com/partner and carries your key in the x-api-key header.

curl https://api.arpmusic.com/partner/me \
  -H "x-api-key: pk_live_4f2c…"
{
  "company":       "Your Company Ltd",
  "environment":   "live",          // or "test"
  "scopes":        ["release:write", "release:read"],
  "linkedAccount": { "id": "66e7…", "name": "Your Company Ltd" },
  "webhookUrl":    "https://your-system.example.com/arp/webhook"
}

Everything you create belongs to your ARP Music account. You never see, and can never reach, anybody else’s.

Test first

Ask your account contact for a test key. You will get one that starts pk_test_, alongside your live key.

It is the same API, the same base URL, the same everything — the only difference is where what you write ends up.

With a test keyLiveTest
Uploads reach storageYesYes
Releases are created and readable by youYesYes
Webhooks fire, signed the same wayYesYes
Reviewed by ARP Music before going furtherYes—
Ever visible in a real catalogue or reportYes—

Test rows are hidden at the database level rather than filtered out by each screen, so there is no query anywhere that can accidentally include them. Nothing you do with a test key needs cleaning up, and nothing you do with it can be seen by anybody at ARP Music.

The environment is in the key

A key pasted into the wrong config is visible on sight — pk_test_… against pk_live_… — rather than discovered later when rehearsal uploads turn up somewhere real. GET /partner/me also tells you which one you are holding.

Every webhook event, on demand

Approvals and rejections happen when a reviewer here gets to them, which is no use when you are testing a handler on a Tuesday afternoon. So move your own test release and watch your endpoint receive it.

POST /partner/releases/REL-2026-0412/simulate 
{ "status": "approved" }

pending needs_fix approved delivered rejected taken_down

Each fires the same webhook a real change does, signed the same way. Add a reason on rejected or needs_fix to test how you render one.

Test keys only, and only on your own test releases. A live key gets a 403 — live releases move when a reviewer moves them.

Before you go live

Worth having done at least once against the test key:

  • A multipart upload with one part deliberately retried.
  • A repeated POST /partner/releases with the same externalId — confirm you get the same release back rather than a second one.
  • A webhook with a deliberately wrong signature — confirm you reject it.
  • A webhook replayed several minutes later — confirm the timestamp check rejects it.
  • ?updatedSince= after leaving your endpoint down for a while — confirm you catch up.
  • A 429, by exceeding a limit on purpose — confirm you wait rather than hammer.

Then send us one real release on the live key before switching the rest across.

1 Send us the file

You can skip this section entirely if you host your own media: send us the URL in step 2. Both are supported and always will be.

Small files, under 50 MB, with a known size

POST /partner/uploads

Request

{
  "fileName":    "cover.jpg",
  "contentType": "image/jpeg",
  "category":    "image",
  "size":        204800
}

Response

{
  "mode":      "single",
  "uploadUrl": "https://…",
  "fileUrl":   "https://…"
}

PUT the bytes to uploadUrl. Use fileUrl in step 2. The URL expires after 15 minutes.

Large files

Anything 50 MB or larger comes back as a multipart upload, in 10 MB parts. So does anything sent without a size: an unknown size is treated as large, because guessing small and being wrong fails at the end of a long upload rather than at the start.

fileName is the only required field.

POST /partner/uploads 
{
  "mode":     "multipart",
  "key":      "partner-uploads/…",
  "uploadId": "…",
  "partSize": 10485760,
  "fileUrl":  "https://…"
}

Split the file into partSize chunks.

POST /partner/uploads/parts 
{ "key": "…", "uploadId": "…", "partNumbers": [1, 2, 3] }

Ask a block at a time rather than all at once — a URL signed too long before it is reached will have expired. PUT each chunk and keep the ETag from the response header.

POST /partner/uploads/complete 
{
  "key": "…", "uploadId": "…",
  "parts": [{ "partNumber": 1, "eTag": "…" }]
}

2 Create the release

POST /partner/releases 
{
  "externalId":       "REL-2026-0412",
  "title":            "AKASHE BATASE",
  "primaryArtist":    ["Moriom Islam"],
  "featuringArtists": ["Moon"],
  "label":            "TEC Music",
  "genre":            ["Country Pop"],
  "language":         "Bengali",
  "releaseDate":      "2026-08-25T12:00:00Z",
  "channel":          "ArtistNameVEVO",
  "videoUrl":         "https://…",
  "imageUrl":         "https://…"
}

Every field

Three are required. Everything else is optional and simply absent from the release if you leave it out.

FieldTypeRequiredNotes
titlestringYesThe release title. Trimmed.
primaryArtiststring[]YesAt least one name. A comma-separated string works too.
videoUrlurlYesA URL you host, or the fileUrl from step 1. video is accepted as an alias.
externalIdstringNoYour own id. See idempotency below.
imageUrlurlNoCover art. image and thumbnail are accepted as aliases.
featuringArtistsstring[]NoComma-separated string also accepted.
labelstringNo
genrestring[]NoComma-separated string also accepted.
languagestringNo
releaseDateISO 8601NoMust carry a timezone — see below.
isrcstringNoSend your own if you have one; otherwise leave it blank.
channelstringNoThe VEVO channel name it should go to.
descriptionstringNo
keywordsstring[]NoComma-separated string also accepted.
composer, producer, editor, musicDirectorstringNo
copyrightYearnumberNo

Anything else in the body is ignored

Deliberately: status and which environment a release belongs to are ours. A release always arrives pending, and which environment it lands in comes from the key, never from the body.

Send it twice on purpose

externalId is your own id, and sending it buys you two things: a repeated call returns the release you already made — same id, 200 and Already created rather than 201 — instead of creating a second one, and you can look anything up by your id rather than storing ours.

Without it, a retried request after a timeout creates a second release. With it, retrying is safe.

releaseDate must carry a timezone

2026-08-25T12:00:00Z or 2026-08-25T18:00:00+06:00. A date with no zone is rejected outright, rather than silently read as UTC.

2b Fix and resubmit

If a reviewer sends a release back with needs_fix, correct it and it returns to review automatically.

PATCH /partner/releases/REL-2026-0412 
{ "primaryArtist": ["Corrected Name"] }

Send only the fields that changed — anything else on the release is left untouched. This only works while the release is in needs_fix; any other status returns 409. On success the release goes back to pending and reason is cleared.

3 Follow what happens

GET /partner/releases?updatedSince=2026-08-19T00:00:00Z

updatedSince is how a dashboard catches up after being offline: everything that changed, nothing that did not. Also filter by isrc or externalId, and page with page/limit (max 100).

GET /partner/releases/REL-2026-0412 
{
  "id":                     "66e7…",
  "externalId":             "REL-2026-0412",
  "isrc":                   "QT6X62690001",
  "isrcAssignedByPlatform": false,
  "status":                 "approved",
  "statusDetail":           "Approved.",
  "reason":                 null,
  "videoUrl":                null
}

Our id or yours — both work in the path, and so does the reference we return.

referencestringA short number for quoting in an email.
externalIdstring | nullYours, if you sent one.
isrcstring | nullNull unless you supplied one.
statusenumOne of the six below.
statusDetailstringThe same thing in a sentence.
reasonstring | nullSet on needs_fix and rejected.
videoUrlurl | nullThe live link, present once delivered — not the file you sent.
createdAt / updatedAtISO 8601updatedAt is what updatedSince compares against.
StatusWhat it means

needs_fixreason says what. Edit and resubmit
approvedAccepted

rejectedreason says why. Terminal
taken_downRemoved after being live

Or be told

Set a webhook once and we call you whenever any of that changes — including when a reviewer here approves something, which is the case you cannot poll for usefully.

Your webhook key is its own key

Managing a webhook uses a key with only the webhook:manage scope — never bundled with a release/upload/channel key. Ask your account contact for one specifically. It cannot create or read releases, and your release key cannot touch the webhook.

PUT /partner/webhook 
{ "url": "https://your-system.example.com/arp/webhook" }

The response carries a signing secret. It is shown once, and it is NOT your API key — a different credential, used only to verify deliveries. The URL must be https.

POST /partner/webhook/test

Fires one signed test event immediately and reports back exactly what happened — use this before relying on any real event.

{
  "delivered": false,
  "responseStatus": 404,
  "error": "Your endpoint answered 404."
}

Lost the secret? Call PUT /partner/webhook again with {"rotateSecret": true} — both the old and new secret verify for 24 hours so nothing breaks mid-rotation.

Events

release.needs_fix release.approved release.delivered release.rejected release.taken_down channel.approved channel.rejected

Every delivery has the same envelope:

{
  "event":       "release.approved",
  "environment": "live",
  "sentAt":      "2026-08-25T12:00:03.000Z",
  "data":        { // same shape as GET /partner/releases/:id }
}

Verify every delivery

// Headers: x-arp-timestamp, x-arp-signature: v1=<hex>
const expected = 'v1=' + crypto
  .createHmac('sha256', SECRET)
  .update(`${req.headers['x-arp-timestamp']}.${rawBody}`)
  .digest('hex');

// Constant-time, and refuse a timestamp older than five minutes.
if (!crypto.timingSafeEqual(
      Buffer.from(expected), Buffer.from(signature))) return 401;

Use the raw request body bytes, not a re-serialized copy — re-serializing can reorder keys and silently break every signature.

Reply 2xx quickly and do the work afterwards. We retry up to four times over about a minute, then stop — and nothing is lost, because everything a webhook carries is also readable from the API.

VEVO channels

A channel is requested, not created: we review it and set it up with VEVO. You see pending, then approved with the live details, or rejected.

POST /partner/channels 
{ "channelName": "ArtistNameVEVO", "artistName": "Moriom Islam" }

channelName is required; artistName is optional but tells the reviewer who it is for. Requesting the same name again while a prior request is pending or approved returns 409; a rejected name can be resubmitted.

GET /partner/channels
POST /partner/channels/:id/simulate 
{ "status": "approved" }

Test keys only, on your own test channel requests — a live key gets 403. Fires the same webhook a real approval/rejection would.

Keys and scopes

A key carries only what it needs. Tell us which of these you use and we will issue it accordingly.

ScopeAllows
release:writeCreate and edit releases
release:readRead status, ISRC, reasons
upload:writeGet upload URLs
channel:writeRequest channels
channel:readRead channels
webhook:manageSet the webhook — issued on its own key only

Keep the key server-side

It is a bearer credential: whoever holds it is you. Never put one in a browser, a mobile app, or a repository.

If a key is exposed, tell us. We issue a replacement and revoke the old one.

Errors

Every failure is JSON with a sentence meant to be read, not a code to look up.

{
  "success": false,
  "message": "videoUrl is required",
  "errorMessages": [
    { "path": "videoUrl", "message": "videoUrl is required" }
  ]
}
CodeMeans
400Something in the request. The message says what
401Key missing, wrong, or revoked
403Key lacks the scope, or is a live key on a test-only route
404Not yours, or not there
409Conflict — a duplicate channel request, or editing a release that isn't in needs_fix
429Too fast
500Ours, not yours. Safe to retry — a create is idempotent on externalId
Questions or a test key — talk to your ARP Music account contact.
